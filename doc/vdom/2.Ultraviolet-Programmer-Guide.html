View Descriptions

Quick Reference

For the impatient, the following code provides the gist of what view description code looks like. These examples resemble those given for DOMVM, the excellent vDOM library that provided much inspiration for Ultraviolet. This is duplication is in part for developers coming from DOMVM to be able to make a like-for-like comparison.

Given:

const uvDom     = new UvDom({ name: "Examples" })
,     vw        = uvDom.define
,     vwIsland  = uvDom.island
,     vwUpdate  = uvDom.update;

Basic:

vw("p", "Hello")                                                                // plain tags
vw("textarea#foo.bar.baz", { rows: 10 }, "Hello")                               // id & class shorthands
vw(".kitty", "Hello")                                                           // "div" can be omitted from tags

vw("input",  {type: "checkbox", checked: true})                                 // boolean attrs

vw("button", { onclick: myFunc }, "Hello")                                      // event handlers
vw("button", { onclick: {f: myFunc, a: anArg }, "Hello")                        // with a bound arg
vw("button", { onclick: {f: myFunc, a: [arg1,arg2] }, "Hello")                  // with multiple bound args

vw("p",      { style: "font-size: 10px;"  }, "Hello")                           // style can be a string
vw("p",      { style: { fontSize: "10px", "z-index": 1 }}, "Hello")             // or an object (camelCase, or quoted with `-`)

vw("h1", [                                                                      // attrs object is optional
    "foo", 123, false, true,                                                    // plain values
    vw("em", "Important!"),                                                     // element with single child
    vw("em", ["Also","Important!"]),                                            // element with multiple children
    vw("br"),                                                                   // void tags without content
    null,                                                                       // will create a comment placeholder
    undefined,                                                                  // will be dropped
    NaN,  Infinity, { valueOf: "Yay!" },                                        // these will be coerced to strings via `$dom`
    injector,                                                                   // inject existing/foreign DOM
    [                                                                           // nested arrays are flattened with almost no performance penalty.
        vw(".foo", { class: "bar" }, [                                          // embedded & attr class get merged: "foo bar"
            "Baz",
            vw("hr"),
            ])
        ],
    ]);

Component:

let navBar = new NavBar({ text: "CArt"  , url: "/cart"  });

vw("#ui", [
    navBar,
    ]);

function NavBar(pagnav) {
    let EXPORTED            = {}
    ,   updateUi            = vwIsland(defineNavBar, EXPORTED);

    const items = Object.freeze([
        { text: "Home"      , url: "/"          },
        { text: "Products"  , url: "/products"  },
        { text: "About Us"  , url: "/about"     },
        ...pagnav,
        ]);

    function defineNavBar() {
        return vw(".nav-bar", items.map((itm) => (vw("a.nav-bar-item", { href: itm.url }, itm.text))));
        }

    return EXPORTED;
    }

Third Party Wrapper:

function ForeignHost() {
    let EXPORTED            = {}
    ,   updateUi            = vwIsland(defineWrapper, EXPORTED);

    function defineWrapper() {
        return vw(".foreign-wrapper", { $insert: insert, $remove: remove });
        }

    function insert(nod,par) {
        // populate nod content; don't change nod itself
        }

    function remove(nod,par) {
        // any required cleanup
        }

    return EXPORTED;
    }
View Details

Technically defined, views in Ultraviolet are the structure produced by UvDom.define(). Each element of the desired DOM is described by an object as follows: { tag: "", atr: {}, chn: [], $uv: {} }. The tag is the name of the element; the attribute structure is the processed contents of the one provided to define; the children array contains the children of the element, either simple values or nested elements.

The attributes structure specifies all HTML attributes for the element, including style which may be provided as a string or object which is processed into a string.

Children can be any JavaScript primitive value or any object which provides a valueOf function. When only one child is needed, the array wrapper may be omitted. Children which are functions are not permitted (nor are they needed, nor especially useful). Of course, one may invoke a function dropping its return value in to the array. For this reason, nested arrays are recursively iterated and their contents added to the node being created as if they were specified at the top level. In this way, it is efficient and convenient to have functions return arrays of children to be added to a view, which makes composing views from many functions effortless and efficient.

The reserved $uv belongs to, and is used by, Ultraviolet and its contents may change at any time without notice. This structure is also attached to the DOM node created and is used by Ultraviolet in rendering. Applications MUST NOT access this object.

To mount a view into the page, use the UvDom update() or island() functions to create an updater which links a view description function to a DOM node:

const { define  : vw
,       update  : vwUpdater
,       insights: vwInsights } = new UvDom({ name: "My Application" });

const   updateUi = vwUpdater(rootView,document.getElementById("app"))

When your application is ready, simply issue a call to updateUi() and the view will be rendered and mounted.

Event Listeners

All event handlers are specified using the onxxx convention, even those for newer events where this is not supported by the DOM.

Event handlers may be a function or a special object like so: { f:function, a:args }. All events are wired into a special function within Ultraviolet, which delegates to the specified function. In this way event handler leaks are impossible, and the listeners are reliably removed when the DOM node is discarded.

One should not use anonymous/arrow functions for capturing data from the current closure. No harm is done by using an arrow function, but it is inefficient and unnecessary.

Special Attributes

In addition to the normal HTML attributes, several special attributes are permitted. These all begin with a $ symbol to avoid name collision with HTML.

Special Features

Attribute Effect
$data Attaches application data to the description and DOM node, which is accessible via UvDom.dataOf(elm,anc).
$debug Activates debugging information for the view layer.

DOM Action Handlers

DOM action Handlers are invoked when specific actions are taken on DOM nodes. Some common requirements are to use a render-completion handler to obtain a reference to the node, and to use insert/remove handlers to add and remove things like a resize observer.

Attribute Effect
$create Invoked when a DOM node is created, before it is attached to the DOM.
$insert Invoked after a DOM node is inserted into the DOM.
$remove Invoked before a DOM node is removed from the DOM.
$render Invoked after a DOM node and its children have been (re)rendered.

DOM handlers receive the affected DOM node and its parent as the first two arguments, following which are any arguments bound to the handler when it was defined.

These same action names (sans “$”) are used to populate the dom section of the insights object.

Examples:

vw("div", {
    $insert: elmInserted,
    $remove: {f:elmRemoved, a:["Custom Arg"]},
    },[
        ...
    ]);

function elmInserted(nod,par) {
    // div was inserted into par
    }

function elmRemoved(nod,par,arg) {
    // nod was removed from par
    // arg => "Custom Arg"
    }
XML Namespaces

SVG, MathML, and other XML-in-HTML nodes can be incorporated by specifying the XML namespace attribute, xmlns. Only the top level namespace is required, unless processing of attributes, such as from mixedCase to kebab-case, is not wanted.

Elements automatically inherit the namespace of their parent when rendered, unless a non-blank namespace is specified. You DO NOT need to specify the HTML5 namespace for any element unless it is declared inside a non-HTML namespace. The HTML5 namespace is the default for rendering.

Note that namespaces are only handled for elements, expecting relatively simple, pragmatic use-cases involving, for example, SVG utilizing shadow-DOM. For fully fledged namespace including attributes, some sort of namespace resolver would have to be supplied and utilized during rendering. There is no plan for this level of XML support at this time.

Child elements automatically inherit the namespace determined for their parent, so an xmlns attribute is only needed on the root of a subtree unless the namespace changes mid-tree. To embed HTML inside an SVG foreignObject, specify the HTML namespace on that element (or the first HTML element) so that the DOM switches back to the appropriate namespace.

Examples of SVG image view-generator functions are as follows:

function svgPath(cls,box,pth) {
    let xmlns = "http://www.w3.org/2000/svg";
    return vw("svg"+cls, {
        xmlns,
        viewBox                     : box,
        style: {
            fill                    : "currentColor",
            color                   : "#080",
            height                  : "1.25em",
            width                   : "1.25em",
            }
        },[
        vw("path",{
            d                       : pth
            }),
        ]);
    }

function svgIcon(idn,cls) {
    let xmlns = "http://www.w3.org/2000/svg";
    vw("svg", {
        xmlns,
        style                       : { fill: "currentColor", height: "1.25em", width: "1.25em" }
        },[
        vw("use", {
            href                    : iconUrl+"#"+idn,
            ariaHidden              : true,
            focusable               : false
            }),
        ]);
    }

function svgPanel(content) {
    let xmlnsSvg  = "http://www.w3.org/2000/svg";
    let xmlnsHtml = "http://www.w3.org/1999/xhtml";
    return vw("svg", {
        xmlns      : xmlnsSvg,
        viewBox    : "0 0 120 60",
        },[
        vw("foreignObject", {
            width  : 120,
            height : 60,
            },[
            vw("div", {
                xmlns : xmlnsHtml,
                class : "svg-panel",
                }, content)
            ])
        ]);
    }

DOM Structural Stability

To achieve its small size and superlative performance Ultraviolet depends on structural stability of the underlying DOM to be able to efficiently identify nodes for reuse when updating a view. For this reason, the view should avoid changing the number of children from render to render, but instead optional elements should be substituted with null when they are not rendered.

It is for this reason that Ultraviolet treats null children as significant elements and creates a comment node placeholder to represent them — this allows elements to be optional from render to render without destabilizing the underlying DOM structure. Conversely, undefined is also permitted for a child, in which case the node is entirely omitted, and this is fine when stability is either not required or not affected, such as rendering a button with optional icons — particularly if the optional element is always omitted in a particular use case.

An unstable structure can negatively affect focus management and cause loss of the insertion point for elements which are recreated rather than updated. It should never result in an incorrect DOM.

Examples

Usually this “element or null” form is the natural way to code an optional element anyway, with a declarative, inline ternary; for example:

function describeDataView() {
    return vw("",
        vw("h3",["User List"]),
        (showList() ? userList : null),
        `Showing ${userList.filteredSize()} of ${userList.totalSize()} records`,
        ]);
    }

However, when something is always either present or omitted, or when structure doesn’t matter, the DOM size can be reduced by using undefined; for example, such as a button generator with optional text and icons

function button(icn1,txt,icn2) {
    return vw("button",[
        icn1 ? genIcon(icn1) : undefined,
        text ? text          : undefined,
        icn2 ? genIcon(icn2) : undefined,
        ]);
    }

For the occasion where an indeterminate number of things must be inserted into a view one should group these inside a container, like so:

function describeDataView() {
    return vw("",
        vw("h3",["User List"]),
        (userInsertions() > 0 ? describeUserInsertions() : null),
        (showList() ? userList : null),
        `Showing ${userList.filteredSize()} of ${userList.totalSize()} records`,
        ]);
    }

function describeUserInsertions() {
    return vw(".user-insertions", userInsertions.map((rcd) => vw(".user-insertion", [...])));
    }

Components

Overview

Unlike React with “Components” and DOMVM with “Views”, Ultraviolet eschews any strong opinion of what constitutes a component by simply working well in a declarative fashion. Components are modules like any other in JavaScript, and to work with another view they simply need to export their update function under the reserved name $dom. For typical components, this is streamlined using the island function.

let updateUi = uvdom.island(defineView, EXPORTED); // My module is now a component
// or
let updateUi = uvdom.island(defineView, EXPORTED).mount(rootElement); // My module is now the root component

To successfully function as a component, a module should be self contained, and maintain a DOM tree reflecting its current state. How a component has its internal state changed is entirely up to the designer of the component and is orthogonal to Ultraviolet — all that matters is that if the state changes the component regenerates its DOM tree via the same update/island function that was exported. This will automatically update the live DOM if the component is already mounted.

This means that in Ultraviolet components are trivially easy to write and have no inherent constraints on their design.

BEWARE, though, that this also means that for a component to update its UI it must be aware that it’s state has changed, which means that sharing mutable state with another component (such as an array of values) should be avoided; instead the component should make a copy of said state, which is subsequently explicitly updated if the parent’s state changes.

Other Considerations

Third-Party Integration

Most third-party code will be integrated with Ultraviolet by either: (a) utilizing the $insert and $remove lifecycle-handlers; or (b) by implementing a very thin layer which exports a $dom function and integrates as a component.

Because of this ability to directly use a DOM subtree, third-party integrations seldom require use of render callbacks; they can simply be allowed to GC when no longer required. But a $remove lifecycle-handler may allow the programmer to facilitate more timely release of resources (like walking the subtree and removing all event listeners). What is required and what is optimal depends on the third-party design.

Optimization

First, Ultraviolet is fast — surprisingly fast — so optimizations are rarely needed. For most complex UIs the total time to describe and render a complex view will be measured in single-digit milliseconds on an aging laptop. But if they do become necessary, the most effective strategy is to think like a teenager and avoid unnecessary work.

Ensuring that the overall DOM structure remains stable in the face of state changes can realize huge improvements in rendering time, since by far the most costly interaction is changing the browser’s DOM. With a stable DOM tree Ultraviolet is able to efficiently avoid wholesale destruction and creation of subtrees and minimally update the existing nodes in the tree.

Another effective strategy is to avoid unnecessary processing while generating the view description. This often entails manipulating the state when it is changed to something more optimal for describing the desired view.

Finally, view descriptions are constant after creation, so saving or predefining and reusing parts of the view that are not affected by state can often lead to realizing some nominal gains. If memoizing the view, it is also recommended that you deep-freeze them as well, including deep-freezing the app-defined $data object.
