Converting from DOMVM

Ultraviolet is at rough parity with DOMVM’s “nano” build. Externally and conceptually Ultraviolet and DOMVM are very similar. The primary differences are: (a) there is only one view description function in place of DOMVM’s eight, (b) the way lifecycle-handlers and special features are specified is cleaner, and (c) components are completely self-contained, with strict isolation from their parent.

In general, what DOMVM refers to as “rendering”, Ultraviolet refers to as “defining”, while “rendering” in Ultraviolet is the process of transforming a view description into actual DOM nodes. Most applications will never explicitly render using Ultraviolet as that is coordinated by a view-updater.

Ultraviolet has sufficient sanity checks that proceeding via trial and error is a viable approach to porting an existing app to use Ultraviolet.

Checklist:

  1. Replace any global DOMVM aliases.
  2. If applicable, adapt the application page mounting.
  3. Change updateUi() functions to just be a constant created with uvDom.island() or uvDom.update().
  4. Adapt components and where they are used. Be careful to ensure that any component calls its own init at the bottom of the module, and is not expecting init to be invoked by the vDOM engine.
  5. Change onxxx attributes to use a plain function or {f:function, a:[args]} object. Change the event handlers to move the event argument to the beginning.
  6. Change lifecycle-handlers to use a plain function or {f:function, a:[args]}object, with the appropriate property name instead of a _hooks object.
  7. Adapt any uses of _data and where they are extracted (uncommon).
  8. Remove DOMVM _key attributes.
  9. Check for any tag names that use DOMVM’s attribute shorthand with, e.g., "div[atr=some-value] notation, and change it to use the attribute object argument.
API Aliases

Typically in a project one will have aliased the various DOMVM API functions to internal names. These are all either eliminated or mapped to the single Ultraviolet define() API:

DOMVM API Ultraviolet Equivalent
createView() N/A: Just instantiate an object or module.
defineComment() N/A: Arbitrary comments are not supported by Ultraviolet.
defineElement() define().
defineSvgElement() define(), specifying attribute xmlns: "http://www.w3.org/2000/svg".
defineText() N/A: Just directly specify the value as a child.
defineView() define().
injectElement() Use any child with a $dom function.
injectView() N/A: Views are not a particular class of thing to be created and injected.

Replace the global DOMVM declaration with the block indicated in the programmer guide Quick Reference.

App Mounting

With Ultraviolet a view updater is optionally initialized with an existing DOM node. For the app root this node is the (usually) configured mount point. The app is realized into the DOM when the updater is first called. Create an updater for the main view specifying the target DOM node at the top of the module, and replace the DOMVM mount() with a call to your updater.

Or, use island() to create the updater, and it’s sub-function mount() to mount it:

let updateUi = uvdom.island(defineView, EXPORTED).mount(rootElm);
App/Component Init

Any initialization is done in the normal module init. There is no separate component init function.

View Updater

In DOMVM creation of a view updater requires a ViewModel reference, and typically must be deferred until after the view is actualized. Typically this results in a tiny updateUi function which invokes the view updater only if it is non-null. This consideration does not exist for Ultraviolet and means that a view updater named updateUI() can be created immediately and the internal function eliminated. Use island() to create a view updater, or more rarely, update().

Components will usually use island, which streamlines exporting the special property for UvDom to recognize them as such.

Event Handlers

Search for all event handlers and change the parameterized form of DOMVM from [fnc,...args] to the Ultraviolet form of {f:fnc,a:[...args]}, or specify just the function if arguments are not required; {f:fnc} is also allowed.

In addition, Ultraviolet provides the event argument as the first argument to event handlers. Search for your event handlers and change them to move the event argument to the first position.

Components

Components are simpler and easier to reason about in Ultraviolet, therefore DOMVM components are altered as follows:

  1. The special DOMVM arguments are eliminated and the arguments are whatever the component needs. Strongly recommended are MyComponent(cfg,ctx), where cfg is the component’s configuration, and ctx is its initial (and perhaps, only) operating context.
  2. To be a child to another Ultraviolet view, the component uses UvDom.island() to create a view updater and export that as $dom. The parent just specifies the module’s exports as a child. Ultraviolet does the tricky bits.
  3. External changes to the component’s state are effected by simply calling exported component methods. Ultraviolet has no opinion on how this ought to be done. Common is to have a updateXxx functions which handle updating the state of the component (see 1).
  4. Ultraviolet components are fully self-contained. If the component changes its state internally it must internally trigger a view update by simply invoking its view updater. If the component is currently part of an active DOM tree the browser will immediately reflect the updated view.
Render Hooks

DOMVM specifies “render hooks” using a special attribute named _hooks, which is an object mapping named event IDs to functions to call when that event occurs. Ultraviolet replaces these with “DOM Handlers” specified using $xxx attributes as listed in the Programmer Guide.

Render callbacks are specified identically to event callbacks (they are in fact rendering events), and receive the node and parent as their standard arguments. Any bound arguments are passed after the standard arguments.

Node Data

DOMVM allows you to attach arbitrary data to a node using _data in the description, and access the data using elm._node.data.

In Ultraviolet, this is done with $data to attach the data, and UvDom.dataOf(elm) to access it.

Node Keys

Ultraviolet does not use or require keys — search for _key and eliminate them.
